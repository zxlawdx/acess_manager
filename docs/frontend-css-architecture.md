# Frontend CSS architecture

This document describes the current Access Manager cascade while the legacy NOC
styles are migrated to the Tangerine design system. It is an architecture map,
not a redesign specification.

## Runtime order

`templates/source/shell_start.html` is the source of truth for stylesheet links.
`templates/index.html` is generated by `tools/build_frontend_template.py` and
must not be edited as the stylesheet registry.

Current order:

1. `style.css` — original global shell, layout, primitives and dark NOC palette.
2. `advanced.css` — advanced/multi-firmware page structure.
3. `support_diagnostics.css` — support diagnostic page.
4. `management.css` — management page.
5. `telecom_console.css` — telecom console feature styles.
6. `adaptive_firmware.css` — adaptive firmware UI.
7. `f6201b_editor.css` — F6201B editor.
8. `neutral_console.css` — neutral console overrides.
9. `brmodelo_workbench.css` — BRModelo workbench.
10. `f6201b_workbench.css` — F6201B workbench.
11. `light_mode_refine.css` — legacy light-mode corrective layer.
12. `dhcp_module.css` — DHCP feature.
13. `tangerine.css` — current global Tangerine compatibility layer.
14. `tangerine_forms.css` — compatibility entrypoint for structured forms.
15. `tangerine_cards.css` — compatibility entrypoint for configuration cards.
16. `tangerine_workflows.css` — workflow layouts and canonical token import.
17. `components/topology.css` — topology component.
18. `components/firmware_inspector.css` — firmware inspector component.
19. `components/shell_layout.css` — shell layout refinements.
20. `components/provider_diagnostics.css` — provider diagnostics component.

The order is regression-tested. Changing it is a behavior change and requires
explicit review because several legacy files still depend on cascade order.

## Layers

### Foundation

`foundation/tangerine_tokens.css` is the only owner of canonical design tokens:

- `--am-color-*`
- `--am-radius-*`
- `--am-space-*`
- `--am-focus-*`
- `--am-transition-*`
- `--am-z-*`
- `--am-font-*`
- `--am-shadow-*`

Light and dark themes change token values rather than duplicating component
rules. Existing `--am-*`, `--ui-*` and original NOC variables are compatibility
aliases and must not gain new independent values.

### Components

Reusable component rules belong in `static/css/components/`.

Current extracted components include:

- `structured_forms.css`
- `configuration_cards.css`
- `topology.css`
- `firmware_inspector.css`
- `shell_layout.css`
- `provider_diagnostics.css`

`tangerine_forms.css` and `tangerine_cards.css` are temporary compatibility
entrypoints so the existing shell asset order remains stable while real rules
live in the component layer.

### Pages and features

Files such as `advanced.css`, `management.css`, `support_diagnostics.css`,
`dhcp_module.css` and firmware-specific styles should contain only page/feature
rules. Shared controls and visual primitives should move to components when a
real reuse boundary exists.

## Legacy corrective layers

### `style.css`

Still owns too many responsibilities: reset, original palette, shell/layout,
navigation and shared components. It remains loaded first for compatibility.
New palette decisions must not be added there.

### `light_mode_refine.css`

Predates the Tangerine theme and contains a large set of light-only corrective
rules with high specificity and `!important`. It is intentionally retained
until equivalent component rules have been migrated and visually validated.
It must not define the canonical `--am-color-*` namespace.

### `tangerine.css`

Still acts as the global compatibility layer and repeats the old `--am-*` token
values. The canonical token stylesheet loads later and therefore owns the final
values. New reusable component rules must not be added to `tangerine.css`;
move them to `components/` instead.

The duplicated legacy token block will be deleted in a later slice when the
large file can be edited and visually validated safely. Until then, tests make
sure no `--am-color-*` definitions appear outside the canonical foundation.

## `!important` policy

Existing `!important` declarations are not removed based only on textual
inspection. The current cascade contains high-specificity legacy selectors and
several late compatibility layers. Remove an `!important` only when the
component has been migrated, its load order is explicit, and light/dark visual
validation confirms the computed style remains unchanged.

The CI inventory prints current `!important` and template inline-style counts so
future cleanup PRs can lower them intentionally and then lock stricter limits.

## State naming

Prefer the existing shared state vocabulary for new work:

- `.is-active`
- `.is-hidden`
- `.is-disabled`
- `.is-loading`
- `.is-error`
- `.is-success`
- `.is-warning`
- `.is-expanded`

Legacy `.hidden`, `.active`, `.locked` and feature-specific states remain valid
until their JavaScript consumers are migrated. Do not rename runtime states in
a CSS-only PR.

## Migration rule

For each block:

1. identify the real owner (foundation, component, page or feature);
2. preserve computed values and selector behavior;
3. move the rules without creating a parallel copy;
4. keep a compatibility entrypoint only when runtime asset order requires it;
5. extend structural tests;
6. perform light/dark visual validation before removing corrective overrides.
